> 适用工程：`D:\上位机\项目学习-墨竹\手敲项目\WinFormsProject`（`TICP.csproj`）
> 实测日期：2026-11-23｜.NET 8 WinForms + SunnyUI + NModbus + Microsoft.Data.Sqlite
> 本文对应的代码**已经写进工程**。目标不是告诉你「改了哪几行」，而是让你理解

## 0. 先看清「闭环」缺在哪

上一版项目能采集、能保存、能查询、能画曲线，但严格说只是**功能拼在一起**，业务上并没有闭环：

| 环节 | 之前的状态 | 补完之后 |
|---|---|---|
| 采集 | 读到原始寄存器值直接显示 | 原始值 → 两点标定 → 物理量 → 合格判定 |
| 显示 | 卡片只有数字，「不合格」是写死的文本 | 显示物理量 + 合格/不合格 + 指示灯变色 |
| 存储 | 只存 8 个通道值 | 额外存 `result` 判定结果与 `ngChannels` 不合格通道 |
| 报警 | 无 | 超差写 `Warn` 日志（限流 10 秒） |
| 通信 | 参数写死 9600/8/N/1，掉线后不会自己连回来 | 参数可配置 + 断线自动重连 + 状态可视化 |
| 统计 | 查询页只有列表 | 合格率统计标签 + CSV 导出（带判定列） |

一句话：**以前是「采到了、存下了」，现在是「采到的值合不合格、谁不合格、不合格率多少，全程可追溯」**。

## 1. 整体数据流（先记住这张图）

```
appconfig.json ──> AppConfigStore.Current ──┐
                                            ├──> mainView 采集任务（后台线程）
yuzhi.json ─────> yuzhiCommon.Current ──────┘              │
                                                           │ 读到 ushort[8] 原始值
                                                           ▼
                                          QualityCommon.Evaluate(raw, cfg)
                                           ├─ TryConvert：两点标定 → 物理量
                                           ├─ IsOk：与测量上下限比较
                                           └─ 汇总 result / ngChannels
                                                           │
                        ┌──────────────────────────────────┼────────────────────┐
                        ▼                                  ▼                    ▼
              simpleView.refreshQuality()         mainCommon.data/oriData    Log.Warn 超差日志
              （BeginInvoke 回 UI 线程）            （Volatile 读写）           （限流）
                                                           │
                                                点「保存数据」按钮
                                                           ▼
                                          dataModel（含判定字段）→ SQLite
                                                           │
                                                           ▼

```

这条链上每一段都有明确职责，**后台线程绝不碰控件，UI 线程绝不做串口 I/O**。

## 2. 配置层：串口参数不再写死

### 2.1 为什么需要

以前 `Connect(comName)` 用默认参数 `9600, 8, N, 1`，从站地址固定 1，轮询间隔硬编码 1000ms。
换一个设备就要改源码、重新编译——这在现场调试时是不可接受的。

### 2.2 新增 `Common/appConfig.cs`

```csharp
public class AppConfig
{
    public string PortName { get; set; } = "";
    public int BaudRate { get; set; } = 9600;
    public int DataBits { get; set; } = 8;
    public string StopBits { get; set; } = nameof(System.IO.Ports.StopBits.One);
    public string Parity { get; set; } = nameof(System.IO.Ports.Parity.None);
    public byte SlaveId { get; set; } = 1;
    public ushort StartAddress { get; set; } = 0;
    public int ChannelCount { get; set; } = 8;
    public int PollIntervalMs { get; set; } = 1000;
    public int ReconnectIntervalMs { get; set; } = 3000;
    public bool AutoReconnect { get; set; } = true;

    public StopBits ToStopBits() =>
        Enum.TryParse<StopBits>(StopBits, true, out var v) ? v : StopBits.One;
    // ...
}
```

三个关键点：

1. **枚举存字符串**：`StopBits` / `Parity` 直接序列化成枚举数字也能用，但 JSON 里写成 `"One"` / `"None"` 人一眼能看懂，改起来不会填错数字。读取时用 `Enum.TryParse` 兜底。
2. **`Clamp()` 夹取非法值**：有人把 `PollIntervalMs` 改成 0，循环就会把串口打成死机；夹到 `[100, 60000]` 毫秒。这是「配置驱动的循环」必须有的防御。
3. **首次运行生成默认文件**：`AppConfigStore.Load()` 读不到就 `Save()` 一份，用户直接改 JSON 就能调参。

配置文件位置：`AppContext.BaseDirectory/appconfig.json`（和 `data.db`、`yuzhi.json` 同目录）。

### 2.3 连接时应用配置

`mainView.TryConnect()` 把配置真正传给通信对象：

```csharp
bool ok = mainCommon.modbusRtuClient.Connect(portName, cfg.BaudRate, cfg.DataBits,
    cfg.ToStopBits(), cfg.ToParity());
if (ok) AppConfigStore.Save();   // 连接成功才记住端口
```

> 为什么只在成功时保存？避免把用户临时选错的端口写进配置，下次启动连不上还找不到原因。

## 3. 判定服务：把「阈值」从摆设变成规则

### 3.1 复用已有的标定方法

`yuzhiModel` 里其实早就有两个现成方法，只是没被用起来：

```csharp
public bool TryConvert(double raw, out double value)  // 两点线性标定
public bool IsOk(double value)                        // 是否在测量上下限内
```

两点标定公式：

```
value = valueLow + (raw - rawLow) * (valueHigh - valueLow) / (rawHigh - rawLow)
```

举例：`liangjuDown=0, liangjuUp=1000`（原始计数），`jiaozhunDown=0, jiaozhunUp=100`（物理量），
那么原始值 500 → 物理量 50.00。

### 3.2 新增 `Common/qualityCommon.cs`

```csharp
public static QualityResult Evaluate(ushort[] raw, yuzhiConfig config)
{
    for (int i = 0; i < count; i++)
    {
        yuzhiModel m = config.channels[i];
        values[i] = m.TryConvert(raw[i], out double v) ? v : raw[i];
        ok[i] = m.IsCalibrated ? m.IsOk(values[i]) : null;   // null = 未标定
        if (ok[i] == false) ng.Add(i + 1);
    }
    string result = ng.Count > 0 ? "不合格"
                  : anyUncalibrated ? "未标定" : "合格";
    // ...
}
```

三个设计决定：

- **未标定用 `bool?` 的 `null` 表示**，而不是 `false`。否则没配阈值时 8 个通道全报「不合格」，是误报。
- **整体判定有优先级**：任一通道超差 → `不合格`；否则有未标定 → `未标定`；全合格才 `合格`。
- **纯逻辑、不引用 WinForms**：所以能在控制台工程里直接跑测试，不需要启动窗体。

### 3.3 接入采集任务

`mainView.StartRead()` 里，读到寄存器后多三步：

```csharp
ushort[] raw = mainCommon.modbusRtuClient.ReadHoldingRegisters(
    cfg.StartAddress, (ushort)cfg.ChannelCount);

QualityResult q = QualityCommon.Evaluate(raw, yuzhiCommon.Current);
for (int k = 0; k < q.Values.Length && k < mainCommon.data.Length; k++)
{
    Volatile.Write(ref mainCommon.oriData[k], raw[k]);   // 原始值
    Volatile.Write(ref mainCommon.data[k], q.Values[k]); // 物理量
}
simpleViews[i].refreshQuality(q.Values[i], q.Ok[i]);     // 后台线程调，内部 BeginInvoke
```

注意 `mainCommon.data` 的语义变了：**以前存原始计数，现在存物理量**。
趋势曲线读的是保存后的 `data1..8`，现在画的也是工程量，更有意义。

### 3.4 卡片显示：指示灯真的会变色

`simpleView.refreshQuality(double value, bool? ok)`：

```csharp
uiTextBox7.Text = value.ToString("F2", CultureInfo.InvariantCulture);
uiTextBox3.Text = ok switch { true => "合格", false => "不合格", null => "未标定" };
uiTextBox3.ForeColor = ok switch { true => Color.Green, false => Color.Red, null => Color.Gray };
uiLedBulb1.Color = ok switch { true => Color.LimeGreen, false => Color.Red, null => Color.Gray };
```

新增的 `PostToUi(Action)` 把上一版的句柄校验和 `BeginInvoke` 封装起来，两个刷新方法共用，
避免「每加一个刷新点就复制一遍跨线程代码」。

## 4. 断线自动重连

### 4.1 状态机思路

后台循环每一轮先判断连接状态：

```
未连接 + 用户没主动断开 + 配置允许自动重连 + 距上次尝试 >= 间隔
    → 尝试连接（静默，不弹窗）→ 更新 UI 状态
已连接 → 读寄存器 → 判定 → 刷新
读异常 → ModbusRtuClient 内部已 Disconnect → 写日志 → 下一轮自动重连
```

### 4.2 关键代码

```csharp
if (!mainCommon.modbusRtuClient.IsConnected &&
    !manualDisconnect && cfg.AutoReconnect &&
    !string.IsNullOrWhiteSpace(cfg.PortName) &&
    Environment.TickCount64 - lastReconnect >= cfg.ReconnectIntervalMs)
{
    lastReconnect = Environment.TickCount64;
    TryConnect(cfg.PortName, false);          // 自动重连不弹窗
    UpdateConnectionUi(IsConnected, IsConnected ? "已连接（自动）" : "重连中…");
}
```

三个必须注意的点：

1. **限流**：`lastReconnect` 时间戳防止端口被占用时每秒狂试，日志和串口都被冲爆。
2. **用户主动断开要能压过自动重连**：`manualDisconnect` 用 `volatile`，点击「断开」时置 `true`，点「连接」时置 `false`。否则用户点了断开，下一秒又连上了。
3. **后台线程更新 UI 也走 `BeginInvoke`**：`uiLight1` 属于 `Form1`，`uiLabel3` 属于 `mainView`，统一封装在 `UpdateConnectionUi()` 里，还要检查 `IsDisposed`。

按钮也变成了「连接 / 断开」切换，状态文字显示 `COM3 已连接` / `重连中…` / `无连接（已手动断开）`。

## 5. 数据层：判定入库、旧库迁移、统计

### 5.1 模型加两个字段

```csharp
public string result { get; set; } = "未标定";   // 合格 / 不合格 / 未标定
public string ngChannels { get; set; } = "";     // "1,3,5"
```

### 5.2 旧库迁移（最容易漏的一步）

`CREATE TABLE IF NOT EXISTS` 对**已存在的表不会加列**。所以老用户的 `data.db` 会在 `Insert` 时报
「no such column: result」。修法是建表后查 `PRAGMA table_info`，缺哪列补哪列：

```csharp
cmd.CommandText = "PRAGMA table_info(DataModel);";
using (var reader = cmd.ExecuteReader())
    while (reader.Read()) existing.Add(reader.GetString(1));

foreach (string col in new[] { "result", "ngChannels" })
{
    if (existing.Contains(col)) continue;
    cmd.CommandText = $"ALTER TABLE DataModel ADD COLUMN {col} TEXT;";
    cmd.ExecuteNonQuery();
}
cmd.CommandText = "UPDATE DataModel SET result = '未标定' WHERE result IS NULL OR result = '';";
```

这是**幂等迁移**：跑一次和跑十次结果一样。同时建了时间索引：

```sql
CREATE INDEX IF NOT EXISTS IX_DataModel_testTime ON DataModel(testTime);
```

### 5.3 保存时重新判定

`mainView.uiButton3_Click` 不是简单读 `mainCommon.data`，而是从 `oriData` 快照**重新算一次判定**：

```csharp
ushort[] snapshot = new ushort[8];
for (int i = 0; i < snapshot.Length; i++)
    snapshot[i] = Volatile.Read(ref mainCommon.oriData[i]);
QualityResult q = QualityCommon.Evaluate(snapshot, yuzhiCommon.Current);
record.result = q.Result;
record.ngChannels = q.NgChannels;
```

为什么重新算？因为界面显示的数值可能被隐藏/切页跳过刷新，**库里的数据必须与判定同源**，
不能相信「界面上看起来是什么」。

### 5.4 合格率用 SQL 算

```csharp
SELECT COUNT(*), SUM(CASE WHEN result = '不合格' THEN 1 ELSE 0 END)
FROM DataModel WHERE ...;
```

不要让数据库把几万行拉到内存再 `foreach` 数——这是面试里常被追问的性能意识。

## 6. 查询页：判定列、合格率、CSV 导出

### 6.1 动态创建控件，不动 Designer

判定字段是新增的，Designer 里没有对应列和标签。我在 `totalView` 构造函数里用代码创建：

```csharp
resultColumn.DataPropertyName = "result";      // 绑定到 dataModel 新字段
ngColumn.DataPropertyName = "ngChannels";
dataGridView1.Columns.Add(resultColumn);
dataGridView1.Columns.Add(ngColumn);

statsLabel.Location = new Point(875, 21);      // 顶部工具栏右侧
uiPanel1.Controls.Add(statsLabel);
```

> 为什么不改 Designer？`*.Designer.cs` 是工具生成的代码，手改容易在可视化设计器里被覆盖。
> 加几列、加个标签这种小扩展，在代码里做更稳。

### 6.2 CSV 导出（原来的空按钮）

```csharp
using var dialog = new SaveFileDialog { Filter = "CSV 文件 (*.csv)|*.csv" };
if (dialog.ShowDialog(this) != DialogResult.OK) return;
File.WriteAllText(dialog.FileName, sb.ToString(), new UTF8Encoding(true));
```

两个细节：

- `new UTF8Encoding(true)` 写入 **BOM**，Excel 双击打开中文才不会乱码；
- 字段用 `Csv(value)` 包一层双引号并转义内部引号，`"1,3"` 这种带逗号的值才不会被拆成两列。

没用 Excel 互操作库（EPPlus / ClosedXML）：CSV 无 Office 依赖，工控机上更省事。
如果岗位明确要求 `.xlsx`，再引入 EPPlus 也不迟。

## 8. 面试怎么讲这个项目

按「需求 → 设计 → 实现 → 验证」四段讲，不要报菜名：

> 这是一个八通道尺寸测量上位机。业务上要求实时采集、自动判定合格性、数据可追溯。
> 我把系统分成配置层、通信层、判定层、数据层和展示层：
> 串口参数用 JSON 配置并做了取值夹取；采集跑在 `Task` 里，断线按间隔自动重连；
> 原始值经过两点标定后与阈值比较，判定结果随采样一起入库；
> 跨线程更新统一用 `BeginInvoke`，共享数据用 `Volatile`；
> 旧库用 `PRAGMA table_info` 做幂等迁移，避免升级后丢数据。
> 验证方面用临时控制台工程直接测判定和数据层，不需要接硬件。

容易被追问的点，提前准备：

- **为什么不用 `Invoke` 而用 `BeginInvoke`？** 后台线程同步等 UI 会在窗体关闭/句柄重建时卡死。
- **未标定为什么是 `null` 不是 `false`？** 避免没配阈值就全报不合格。
- **合格率为什么在 SQL 里算？** 避免把全部记录读进内存；日期列建了索引。
- **自动重连会不会造成风暴？** 有 `ReconnectIntervalMs` 限流，用户主动断开有 `manualDisconnect` 压过。

## 10. 还没做的（诚实边界）

这一轮补的是**现有 WinForms + Modbus RTU 技术栈内的业务闭环**，下面这些属于技术栈升级，
不是「补功能」，没有做：

- Modbus TCP / OPC UA / 主流 PLC 协议对接
- WPF + MVVM 重构
- 用户权限、配方管理、MES 对接、报警弹窗与声音
- 单元测试项目（目前靠临时控制台工程验证）

想继续提升的话，建议顺序：**先加 Modbus TCP（通信层抽象出接口）→ 再抽依赖注入 → 最后考虑 WPF/MVVM**。
