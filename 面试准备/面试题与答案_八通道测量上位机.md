**参考答案**（口述 + 手画）：


### A4 ⭐⭐ 如果重做，你会怎么改？（区分度最高的一题）

**参考答案**（分四层，按重要性）：
1. **架构**：全局静态 `mainCommon.modbusRtuClient` 改成 `IModbusClient` 接口 + 依赖注入，采集逻辑从 `mainView` 抽到 `AcquisitionService`，页面通过事件/消息订阅数据，不再靠全局数组隐式传递。

4. **可测试性与功能**：补 xUnit 单测、报警去重/确认/声音与报警记录表、配置热重载、多从站轮询、日志结构化。

**加分**：明确说"练习项目量级很小，我改的重点是正确性和可测性，不是盲目上分布式/高并发"。

## B. C# / .NET 基础

### B1 ⭐⭐ `volatile` 关键字解决什么问题？项目里哪里用了？

**参考答案**：`volatile` 禁止编译器/CPU 对该字段的读写做重排序与缓存优化，保证「一个线程写、其他线程读」时的可见性，**但不保证复合操作原子性**（`i++` 仍不安全）。
项目里三处：`mainView.manualDisconnect`（UI 线程写、采集线程读）、`channelsVisible`（隐藏通道标志，采集线程不直接读控件）、以及 `mainCommon.oriData/data` 数组元素用 `Volatile.Write/Read`。

**追问**：`为什么不用 lock？` → 单写多读的布尔标志用 `volatile` 更轻、不会阻塞采集循环；`lock` 适合需要保护一段复合逻辑的场景，项目里只在 `Log.cs` 写文件用了 `lock`。

---

### B2 ⭐⭐⭐ `volatile` 能修饰 `double` 吗？为什么 `data` 数组用 `Volatile.Write`？

**参考答案**：不能。C# 的 `volatile` 只允许 `bool/byte/sbyte/short/ushort/int/uint/char/float`、引用类型和以此为基础的枚举；`long` / `double` / `decimal` 在 32 位环境下不保证原子读写，编译器会报 CS0677。
所以 `mainCommon.data`（`double[8]`）不能声明成 `volatile double[]` 的元素，改用 `System.Threading.Volatile.Write(ref mainCommon.data[k], value)` / `Volatile.Read(...)`，由运行时对该元素做带内存屏障的原子读写。

**加分**：`Volatile.Write` 是 release 语义、`Volatile.Read` 是 acquire 语义；它们保证的是该次读写的可见性，**不保证整个数组的一致性**（见 B9 / E6）。

---

### B3 ⭐⭐ 为什么用 `bool?` 三态，而不是 `bool` 加一个「是否已标定」字段？

**参考答案**：`bool?` 把「没有判定依据」编码进类型本身，`null` 就是未标定，编译期就会迫使调用方处理三态；`Ok[i] == false` 才进超差列表，`Ok[i] == null` 只标记 `anyUncalibrated`。如果用 `bool` + 额外标志，两个字段可能不一致，任何漏判分支都会把未标定通道当成不合格，直接导致误报和错误统计。
项目里 `IsCalibrated` 仍保留在 `yuzhiModel`（判断四个标定参数是否都能解析），但对外结果统一是 `bool?`。

**追问**：`Nullable<bool> 的 == false 会怎样？` → `null == false` 为 `false`，所以 `if (ok[i] == false)` 只捞真正的超差，这正是三态好用的地方；用 `if (!ok[i].Value)` 会在 `null` 时抛 `InvalidOperationException`。

---

### B4 ⭐⭐ 采集为什么用 `Task.Run(async …)` + `await Task.Delay`，不用 `Thread` 或 `WinForms.Timer`？

**参考答案**：
- `WinForms.Timer` 的 `Tick` 跑在 UI 线程，串口读取是阻塞 I/O（ReadTimeout 1000ms），会直接卡住界面；代码注释里明确写了 `//timer1.Start(); 会卡顿，已用异步方式代替`，`timer1` 现为保留的死代码。
- `Task.Run` 把循环放到线程池，`await Task.Delay(ms, token)` 是**异步等待不占线程**，且能被 `CancellationToken` 立即唤醒退出；`Thread.Sleep` 会霸占线程且无法取消。
- 裸 `Thread` 需要自己管生命周期、异常和取消，CTS 是更现代的做法。

**加分**：`Task.Run(async () => …)` 返回的是 `Task`（内部 async lambda 被正确 unwrap，不会变成 `Task<Task>`，因为 `Task.Run(Func<Task>)` 有专门重载）。

---

### B5 ⭐⭐⭐ 为什么 `CancellationTokenSource` 只 `Cancel()` 不 `Dispose()`？

**参考答案**：`mainView` 构造里 `Disposed += (s,e) => readCTS.Cancel();`。后台任务在循环中还要访问 `readCTS.Token`、把它传给 `Task.Delay(ms, token)`；若在窗体销毁瞬间 `Dispose()` 了 CTS，后台任务再取 Token 可能抛 `ObjectDisposedException`，变成一次无意义的异常日志甚至掩盖真正的退出路径。这里 CTS 生命周期随页面对象，页面本身在 `Form1` 里缓存不 Dispose，让 GC 回收即可。

**追问**：`那不会泄漏吗？` → 单个页面一个 CTS、Cancel 后任务会退出循环，没有注册回调和计时器，属于可接受的取舍；若要严格，可在任务的 `finally` 里确认循环结束后再 Dispose，前提是所有取 Token 的动作都已完成。

---

### B6 ⭐⭐ `try/catch` 为什么必须写在 `while` 里面？

**参考答案**：写在 `while` 外面，任何一次串口异常都会跳出整个循环，采集永久停止，只能重开程序；写在循环内，单次失败被 catch、记录（限流）日志、标记断线，下一轮继续走自动重连逻辑。这是"长驻采集任务"的基本骨架：`while (!token.IsCancellationRequested) { try { … } catch { … } await Delay(token); }`。

**加分**：`catch (OperationCanceledException) { break; }` 要单独放在通用 `catch (Exception)` 之前，否则取消会被当成故障记日志。

---

### B7 ⭐ `static class mainCommon` 的全局状态有什么风险？

**参考答案**：`oriData` / `data` / `modbusRtuClient` / `sqlHelper` 都是静态可变字段，任何地方都能改，构成隐式耦合；无接口抽象无法 mock，多线程下需要靠 `Volatile` 手工维护可见性；多个窗体实例（如果将来有）会共享同一份数据；测试之间会互相污染。
改进：定义 `IAcquisitionState` / `IModbusClient`，通过构造函数注入；状态用不可变快照 + `Interlocked.Exchange`。

**追问**：`为什么当初还这么写？` → 「练习项目为了快速打通闭环，静态类最省事；我清楚它的代价，所以把纯判定逻辑抽成无状态的 `QualityCommon`，至少核心业务是可测的。」

---

### B8 ⭐⭐ 为什么到处用 `CultureInfo.InvariantCulture`？

**参考答案**：标定参数在 JSON 里以 `string` 保存，解析/格式化如果跟随系统区域设置，在德语/法语等用逗号作小数点的机器上 `"17.5"` 会解析失败或变成 175；`double.ToString("F2", InvariantCulture)`、`TryParse(..., NumberStyles.Float, InvariantCulture, out v)` 保证跨机器一致。数据库里 `testTime` 固定 `yyyy-MM-dd HH:mm:ss`，同样配 `TryParseExact` + InvariantCulture。

**加分**：这也是「数值为什么不该存 TEXT」的一个具体论据。

---

### B9 ⭐⭐⭐ 对数组元素做 `Volatile.Write` 是"原子快照"吗？

**参考答案**：不是。每次只保证**单个元素**的读写可见性。采集线程写 8 个元素，保存按钮逐个 `Volatile.Read` 8 次，中间可能被采集线程插入，读到的 8 个值分属两次采样（TOCTOU / tear）。当前 1s 轮询 + 手动点保存，碰撞概率低，但语义上不严谨。
正确做法：把 8 路数据 + 采集时刻 + 序号打包成不可变 `RecordSnapshot`，采集端一次构造完用 `Interlocked.Exchange(ref _current, snapshot)` 整体发布；保存端一次 `Volatile.Read(ref _current)` 拿到完整一致的一帧。或用 `lock`/`ReaderWriterLockSlim` 包住读写。

**这题是本项目最容易被深挖的设计缺陷，务必主动会答。**

## C. WinForms / UI 线程

### C1 ⭐ 为什么不能从后台线程直接改控件？会报什么？

**参考答案**：WinForms 控件绑定在创建它的 UI 线程且不是线程安全的，跨线程访问会抛 `InvalidOperationException: 线程间操作无效: 从不是创建控件"xxx"的线程访问它`（在调试器附加时更严格）。必须把更新封送回 UI 线程：`Invoke` / `BeginInvoke`，或用 `SynchronizationContext`、`Progress<T>`。

---

### C2 ⭐⭐⭐ 为什么选 `BeginInvoke` 而不是 `Invoke`？

**参考答案**：
- `Invoke` 是**同步**阻塞，后台线程要等 UI 线程执行完委托；若 UI 线程正在等待后台任务、或窗口句柄正在重建/销毁，容易卡死甚至死锁；采集循环每 1s 一帧，阻塞会拖慢节奏。
- `BeginInvoke` 是**异步投递**（`PostMessage` 到 UI 消息队列），后台线程立刻返回，UI 忙时最多积压少量帧，不会拖住采集。
- 代价：委托执行有延迟、可能积压，所以要点是「帧数据放全局数组，UI 只投递一次刷新动作」，而不是把数据塞进委托队列。

项目里 `mainView.UpdateConnectionUi` 和 `simpleView.PostToUi` 都是这个模式。

---

### C3 ⭐⭐ `IsDisposed` / `IsHandleCreated` 校验和 `catch (InvalidOperationException)` 各防什么？

**参考答案**（`simpleView.PostToUi`）：
- `IsDisposed` / `!IsHandleCreated`：**投递前**过滤，控件已销毁或句柄尚未创建时不调用 `InvokeRequired`（访问它本身可能触发句柄创建或抛异常）。
- 委托内部再判一次 `if (!IsDisposed) action()`：**执行时**过滤，因为从投递到执行之间窗口可能已被销毁（异步投递的固有时间差）。
- `catch (InvalidOperationException)`：兜底「校验通过的一瞬间句柄被销毁」的竞态，跳过本帧而不是让采集任务崩掉。

**加分**：这三层是"异步封送 + 动态句柄"场景的标准防御，能讲出「校验与执行之间存在竞态窗口」就是满分。

---

### C4 ⭐⭐⭐ `HandleDestroyed` 和 `Disposed` 有什么区别？为什么定时器/任务只能挂在 `Disposed`？

**参考答案**：
- `HandleDestroyed`：Win32 窗口句柄被销毁时触发，**不代表对象生命周期结束**；句柄常常会被重新创建（`HandleCreated`），例如改变 `Parent`、设置某些需要重建句柄的属性、跨顶层容器移动。
- `Disposed`：控件真正被释放、生命周期结束，不会再回来。

本项目 `FormShowHelper.formShow` 用「改 `Parent` + `Dock=Fill`」切页，会重建句柄；早期把 `readCTS.Cancel()` / `refreshTimer.Stop()` 挂在 `HandleDestroyed`，导致从"阈值设置"切回"数据测量"后采集和刷新永久停止。改为只挂 `Disposed`，且页面在 `Form1` 中缓存复用（`page ??= factory()`，从不 Dispose），问题消失。

**配套**：`Load` 事件在句柄重建后可能再次触发，所以 `mainView_Load` 用 `initialized` 做幂等，防止重复创建 8 张卡片、重复启动采集任务。

---

### C5 ⭐⭐ 讲讲页面切换的实现，`Controls.Clear()` 为什么不 Dispose？

**参考答案**：`FormShowHelper.formShow(UIPage page, UIPanel host)` 做三件事：`host.Controls.Clear()` → `page.Parent = host` → `page.Dock = Fill` + `Show()`。`Controls.Clear()` 只解除父子关系，控件对象还活着，正好配合 `Form1` 里的 `page ??= factory()` 缓存复用（切页保留采集状态、表格绑定、输入内容）。如果 Dispose 掉，缓存字段还持有已释放对象，下次切回来访问就会抛 `ObjectDisposedException`。
`ShowPage<T>` 还用 try/catch 包住页面构造，单页初始化失败（比如 ScottPlot/SkiaSharp 加载异常）只弹提示，不拖垮 `Application.Run`。

**加分**：`mainView` 通过构造函数拿到 `Form1` 的 `uiLight1`，用于后台线程更新主窗体连接灯——这是跨页面共享控件的显式注入，比到处 `((Form1)this.ParentForm)` 强转干净。

### C6 ⭐ 按钮点了没反应，你的排查顺序？

**参考答案**（这是项目里真实踩过的坑，`mainView.Designer.cs` 有注释「原来漏了这行，所以按钮点了没反应」）：

### C7 ⭐ Dock 布局：「隐藏通道」为什么只改一个 `Visible`？

**参考答案**：卡片区 `uiPanel2.Dock = Top`，下方标题与 `DataGridView` 是 `Dock = Fill`。WinForms 布局引擎按 Dock 顺序自动排布，把 Top 面板 `Visible = false` 后，Fill 面板会自动上移占满剩余空间，无需手工改 `Location`/`Size`。所以按钮只切 `uiPanel2.Visible`（并同步 `channelsVisible` 供后台线程判断），不会留下空白。

## D. Modbus / 串口 / 采集链路

### D1 ⭐⭐ 画出 0x03 读保持寄存器的 RTU 请求/响应帧

**参考答案**：
请求（8 字节）：`[从站地址 1B][功能码 0x03 1B][起始地址 2B 高字节在前][寄存器数量 2B][CRC16 2B 低字节在前]`
例：从站 1、起始 0x0000、读 8 个 → `01 03 00 00 00 08 CRC_L CRC_H`
响应：`[地址][0x03][字节数 0x10][16 字节数据（每寄存器 2 字节，高字节在前）][CRC16]`，共 1+1+1+16+2 = **21 字节**。
RTU 靠 **3.5 个字符时间的总线静默**区分帧边界（不是靠固定长度），CRC 为 CRC16/MODBUS，低字节先发。

**追问**：`异常响应长什么样？` → 功能码最高位置 1（`0x83`）+ 异常码（01 非法功能、02 非法地址、03 非法数据值…），且只回一个字节数据。

---

### D2 ⭐⭐ Modbus RTU 与 Modbus TCP 的区别？项目用的是哪个？

**参考答案**：项目只用 **RTU**（`SerialPort` + `ModbusFactory().CreateRtuMaster(new SerialPortAdapter(...))`），**没有实现 TCP**。
- RTU：二进制紧凑帧 + CRC16 + 3.5 字符静默定界，走 RS-485/RS-232，有从站地址。
- TCP：去掉 CRC，前面加 7 字节 MBAP 头（事务标识 2 + 协议标识 2 + 长度 2 + 单元标识 1），走 502 端口，靠 TCP 长度域定界，可多主站并发。
- 两者 PDU（功能码 + 数据）相同，所以扩展 TCP 时业务层几乎不用改——这也是我建议抽 `IModbusClient` 的依据。

**红线**：别把 TCP 说成已实现。

---

### D3 ⭐ 串口参数怎么配？9600 8N1 是什么？为什么要设超时？

**参考答案**：`SerialPort(portName, baudRate=9600, parity=None, dataBits=8, stopBits=One)`，`Handshake=None`，`ReadTimeout=WriteTimeout=1000ms`。8N1 = 8 数据位、无校验、1 停止位。超时是**必须**的：没有超时，从站不响应时读操作会无限阻塞后台任务（甚至拖住退出），`ReadHoldingRegisters` 失败后靠异常进入重连流程。
`AppConfig` 把 12 项参数（端口、波特率、数据位、停止位、校验、从站、起始地址、通道数、轮询间隔、重连间隔、自动重连开关）落 `appconfig.json`，枚举以字符串保存再用 `Enum.TryParse` 转换，`Clamp()` 把 `PollIntervalMs` 限制到 `[100, 60000]`、`SlaveId == 0` 回退 1。

**加分**：只在**连接成功后**才持久化端口，避免把失败的端口写进配置导致下次启动连错。

---

### D4 ⭐⭐⭐ ABCD / CDAB / BADC / DCBA 是什么？float 为什么要 `Array.Reverse`？

**参考答案**：Modbus 寄存器是 16 位大端（高字节在前），但 32/64 位数据如何由多个寄存器拼装没有统一规定，不同厂商有 4 种字序/字节序组合：`ABCD`（大端、寄存器正序）、`CDAB`（寄存器互换）、`BADC`（寄存器内字节互换）、`DCBA`（全反转）。
`ModbusDataConverter.GetBytesFromRegisters` 按 `DataFormat` 重排字节数组；`BitConverter` 在 x86/ARM 上通常是小端，所以对 float/double 需要 `Array.Reverse` 后再 `BitConverter.ToSingle/ToDouble`，否则数值完全不对。项目默认 `DataFormat.ABCD`。

**追问**：`怎么确认设备用哪种？` → 用一个已知值（如 1.0f / 123.456）读回原始寄存器，看字节排列；或查设备手册的"浮点数字节顺序"说明。这是现场联调最常见的坑之一。

---

### D5 ⭐⭐⭐ 讲清楚自动重连状态机

**参考答案**（`mainView.StartRead()`）：
触发条件四个同时成立：① `!client.IsConnected` ② `!manualDisconnect` ③ `cfg.AutoReconnect` ④ `PortName` 非空；再加 `Environment.TickCount64 - lastReconnect >= ReconnectIntervalMs`（默认 3000ms）限流。满足则 `TryConnect(port, showMessage:false)` 静默重连并更新连接灯。
- **为什么要限流**：轮询 1s，若每轮都尝试 `SerialPort.Open()`，会产生大量异常、日志和端口占用，USB 转串口刚插回时还可能反复失败。
- **为什么静默**：后台线程绝不弹 `MessageBox`，只有用户手动点「连接」才允许提示。
- **为什么用 `Environment.TickCount64` 而非 `DateTime.Now`**：前者是系统启动以来的单调毫秒计数，不受用户改系统时间/NTP 校时影响，做间隔判断更可靠，也不涉及时区。
- 同理，采集错误日志、超差报警日志各做 **10s 限流**，防止日志暴涨。

**追问**：`manualDisconnect 为什么要是 volatile？` → UI 线程写、采集线程读，需要可见性保证；否则采集线程可能一直读到旧值，用户点了断开仍被重连。

### D6 ⭐⭐ `ReadHoldingRegisters` 失败为什么要先 `Disconnect()` 再 `throw`？

**参考答案**：串口异常（设备拔出、线松、CRC 错）后，`_isConnected` 标志与实际物理链路可能不一致，串口对象也可能处于坏状态。先 `Disconnect()` 关闭并释放 `SerialPort`/Master、把 `IsConnected` 置 false，抛出后由外层 catch 更新 UI 为"重连中…"，下一轮循环才会进入重连分支。若不置 false，下一轮以为还连着继续读，一直抛异常且不触发重连。

**加分（主动暴露不足）**：封装里只有 `ReadHoldingRegisters` 做了这件事，其它读方法多是 `Console.WriteLine` + `throw`，异常处理不一致，也有一部分日志没走 `Log`；这是我会统一重构的点。

---

### D7 ⭐⭐ 轮询周期 1s 会不会丢数据？要提到 100ms 怎么改？

**参考答案**：先讲清楚取舍：Modbus RTU 是主从问答，上位机只能拿到「轮询瞬间」的值，1s 周期意味着最快 1s 一个采样点，物理上确实会漏掉下位机两次轮询之间的变化——这不是丢包，是采样率设计。
改进路径：① 缩短周期并实测 9600 波特下一帧 RTU 约 21 字节的传输时间（约 20ms 量级）+ 从站响应时间，留出余量；② 单帧批量读 8 个寄存器（项目已经这么做，避免 8 次往返）；③ 通信与入库解耦：采集只入内存环形缓冲/队列，另起消费者批量写库；④ 关键场景改成下位机缓存 + 时间戳批量上传，或换中断/事件上报协议；⑤ 每个采样点带时间戳，避免用 `DateTime.Now` 在入库时才打时间。

### D8 ⭐ `TestConnection` 和 `GetAvailablePorts` 分别做什么？

**参考答案**：`TestConnection(timeoutMs)` 临时改 `ReadTimeout` 读 1 个寄存器做链路测活，用完恢复；`GetAvailablePorts()` 直接返回 `SerialPort.GetPortNames()` 供下拉框枚举。`mainView.FillPorts()` 枚举端口并优先选中配置里上次成功的 `PortName`。

**追问**：`拔掉 USB 后下拉框里的 COM 口还在吗？` → 需要重新枚举；项目在 `Load` 时枚举一次，运行中热插拔不会自动刷新，这也是可改进点。

### D9 ⭐⭐ 从站地址、起始地址、通道数是怎么串起来的？

**参考答案**：`AppConfigStore.Load()` 在 `mainView` 构造时读 `appconfig.json` → `SlaveId = 1` 赋给 `mainCommon.modbusRtuClient.SlaveId`；采集循环 `ReadHoldingRegisters(cfg.StartAddress=0, (ushort)cfg.ChannelCount=8)` 一次读回 8 个 `ushort`，与 `yuzhiConfig.channels`（启动时 `Pad()` 补齐/截断到 8 个）、`QualityCommon.Evaluate` 里的 `Math.Min(raw.Length, config.channels.Count)` 对齐。通道号在结果里从 **1** 开始（`ng.Add(i + 1)`），界面卡片也是 `SetChannelNumber(i+1)`。

**追问**：`配置改成 16 通道会怎样？` → `Evaluate` 按 `Math.Min` 只算配置里有的 8 个，`oriData/data` 数组仍是 8，会截断；要扩展需要同步改数组、表结构（data1..data8）、UI 卡片数和 Designer 表格列——这正是当前"8 通道写死"的设计局限。

## E. 标定 / 判定 / 业务正确性

### E1 ⭐⭐⭐ 写出两点线性标定公式并推导，说明除零保护

**参考答案**（`yuzhiModel.TryConvert`）：取两个标准件：低点原始计数 `rawLow` 对应物理量 `valueLow`，高点 `rawHigh` 对应 `valueHigh`。设线性关系 `value = k·raw + b`，则
`k = (valueHigh - valueLow) / (rawHigh - rawLow)`，`b = valueLow - k·rawLow`
代入得 **`value = valueLow + (raw - rawLow) * (valueHigh - valueLow) / (rawHigh - rawLow)`**。
防护：`rawSpan == 0` 或 `valueSpan == 0` 时返回 `false`（除以零/退化）；四个参数用 `InvariantCulture` 解析，任一失败即视为未标定；结果再检查 `NaN`/`Infinity`；未标定时 `Evaluate` 用原始值 `raw[i]` 回退显示，但 `Ok[i] = null`。

**追问**：`反向量程（rawHigh < rawLow）能算吗？` → 数学上能（斜率为负），要看业务是否允许传感器反向安装；当前代码没有禁止。`raw` 超出 `[rawLow, rawHigh]` 会**线性外推**，可能在量具量程外给出看似合理的数，实际应加范围限制或标记"超量程"——这是我会补的一条。

---

### E2 ⭐⭐ 整体判定为什么是「超差 > 未标定 > 合格」？

**参考答案**：`result = ng.Count > 0 ? "不合格" : anyUncalibrated ? "未标定" : "合格"`。安全优先：只要有任一通道明确超差，这批数据就不可放行，即使其它通道还没标定；全部通道都合格且有标定依据，才能给"合格"。"未标定"是数据可信度不足，不是质量结论，单独成一类便于统计和追溯。

**加分**：`NgChannels` 用 `string.Join(",", ng)` 记录具体通道号（1 起），查询页有独立的「判定」和「不合格通道」两列。

---

### E3 ⭐⭐⭐ 为什么保存时要从 `oriData` 快照**重新判定**，不直接取界面上的值？

**参考答案**（本项目最能体现正确性意识的一题）：
1. 界面显示值可能**过期**：用户隐藏通道卡片时采集线程跳过刷新、切到别的页面时也不会更新卡片，表格里的数未必是最新一帧。
2. 界面显示的是**物理量字符串**（`F2` 格式化后），已经丢了未标定/三态信息和精度，无法再判定。
3. 标定/阈值配置可能在两次刷新之间被改过，界面值属于旧配置。
所以 `uiButton3_Click` 用 `Volatile.Read` 取 `oriData[8]` 原始计数快照 → `QualityCommon.Evaluate(snapshot, yuzhiCommon.Current)` 重新算 → `ToStrings(F2 + InvariantCulture)` → 组装 `dataModel`（含 `result` / `ngChannels`）→ `SqlHelper.Insert`。**库里的数据必须与判定同源同帧**。

**加分**：入库成功才 `bindingList.Add(record)`，写库失败不会在界面留下"假记录"。

### E4 ⭐⭐ `QualityCommon` 为什么不放进 `mainView`？

**参考答案**：单一职责 + 可测试性 + 一致性。判定是纯函数（输入 `ushort[]` + 配置，输出 `QualityResult`），不引用 WinForms、不碰数据库和串口，所以：① 采集线程和保存按钮两处调用同一份逻辑，不会出现"显示一套、入库一套"；② 可以用临时控制台工程（ProjectReference 引用主项目）脱离窗体和硬件实跑验证；③ 将来换 WPF/Web 可以直接复用。

**红线**：绝不在 UI 里重写一遍 if/else 判定——这是这类项目最常见的 bug 来源。

### E5 ⭐⭐ 配置加载做了哪些防御？

**参考答案**：`yuzhiCommon.Load()`：反序列化 `yuzhi.json`，`Pad()` 补齐/截断 `channels` 到 8 个（防止手改 JSON 少通道导致索引越界）、刀补数组补齐到 4 组，逐个 `Normalize()` 把非法数值回退为空串/`"0"`，首次运行自动生成默认文件；`Save()` 用 `WriteIndented` 便于人工检查。`AppConfig.Clamp()` 把轮询间隔钳到 `[100, 60000]`、从站 0 回退 1、枚举字符串 `Enum.TryParse` 兜底。

**追问**：`运行中改 JSON 生效吗？` → 不生效，两个配置都只在页面构造时 `Load()` 一次，没有热重载（可加 `FileSystemWatcher` 或界面「重新加载」按钮）。

### E6 ⭐⭐⭐ 8 路数据逐元素读写会有什么问题？怎么改？（与 B9 同考点，换个问法）

**参考答案**：见 B9。核心词：**非原子快照 / 撕裂读 / TOCTOU**。改法：不可变快照对象 + `Interlocked.Exchange` 一次发布；或 `lock` / `ReaderWriterLockSlim` 包住整组读写；快照里带 `Sequence` 和 `Timestamp`，保存时把序号一并入库，方便追溯。

**面试官真正想听**：你能不能意识到「对单个元素加内存屏障 ≠ 对一组数据加事务」。

### E7 ⭐ 为什么 `dataModel` 的 8 个值用 `string`？

**参考答案**：为了直接绑定 `DataGridView` 的 `DataPropertyName` 并显示 `F2` 格式，也为了兼容早期 JSON/表结构，实现简单。代价：无法在 SQL 里做数值比较/聚合、排序按字典序、跨区域解析风险、精度只能靠格式化约定。改进是 Model 层用 `double?`，持久化用 `REAL`，显示层再格式化（responsibility 归 View）。

**追问**：`那统计合格率怎么做的？` → 用的是 `result` 文本列的 `SUM(CASE WHEN result='不合格' …)`，不依赖 `dataN` 数值列。

## F. SQLite / 数据层

### F1 ⭐ 说说表结构和索引

**参考答案**：单表 `DataModel` 13 列：`Id INTEGER PRIMARY KEY AUTOINCREMENT`、`testTime TEXT`、`projectName TEXT`、`data1..data8 TEXT`、`result TEXT`、`ngChannels TEXT`；`CREATE INDEX IF NOT EXISTS IX_DataModel_testTime ON DataModel(testTime)` 支撑按时间范围查询。当前是单机本地库（`AppContext.BaseDirectory/data.db`），约 14 行历史测试数据。

### F2 ⭐⭐⭐ 旧版本数据库缺列，怎么做的幂等迁移？为什么 `CREATE TABLE IF NOT EXISTS` 不够？

**参考答案**：`CREATE TABLE IF NOT EXISTS` 在表已存在时**什么都不做**，不会补列，所以老库里没有 `result`/`ngChannels`，`INSERT` 直接报 `no such column: result`；也不能让用户手工删库（历史数据会丢）。
迁移四步（`SqlHelper.InitDatabase()`，每次启动都跑，可重复执行）：
1. `PRAGMA table_info(DataModel)` 读出现有列名到 `HashSet<string>`；
2. 缺失的列逐个 `ALTER TABLE DataModel ADD COLUMN result TEXT` / `ngChannels TEXT`（SQLite 的 ADD COLUMN 无法"IF NOT EXISTS"，所以必须先探测）；
3. `UPDATE DataModel SET result='未标定' WHERE result IS NULL OR result=''` 回填历史行；
4. `CREATE INDEX IF NOT EXISTS` 补索引。
已用含 14 行历史数据的旧库验证：迁移后旧行 `result='未标定'`、`ngChannels` 为 NULL。

**加分**：能说清 `ExecuteReader` 里 `reader.GetString(1)` 取的是 `PRAGMA table_info` 结果的 **name** 列（cid=0, name=1）。

---

### F3 ⭐⭐ `last_insert_rowid()` 为什么要和 INSERT 用同一个连接？

**参考答案**：`last_insert_rowid()` 返回的是**当前连接**上最后一次成功插入的 rowid，是连接级状态而非全局；换连接（尤其连接池复用/新建）可能拿到 0 或别人的 Id。项目在 `Insert` 里用同一个 `SqliteConnection` 先 `ExecuteNonQuery()` 执行参数化 INSERT，再单独 `SELECT last_insert_rowid()` 用 `ExecuteScalar()` 取 Id。

**追问**：`写成 INSERT ...; SELECT last_insert_rowid(); 一条语句行吗？` → 在 Microsoft.Data.Sqlite 下可行（驱动会推进多结果集，`ExecuteScalar` 能拿到正确 Id，不是 bug），项目改成两步写法只是为了语义更明确、避免依赖驱动的隐式行为。

---

### F4 ⭐⭐ 为什么 .db 文件删不掉 / 被占用？

**参考答案**：`Microsoft.Data.Sqlite` 默认开启连接池，`using` 释放连接只是归还池中，底层文件句柄仍被进程持有，Windows 上就不能删除/覆盖文件。测试或升级时先 `SqliteConnection.ClearAllPools()`（或在连接串里 `Pooling=False`），并确保所有 reader/command/connection 都已释放。
项目代码里没有显式管理连接池，每个方法 `using var connection = new SqliteConnection(...)` 即开即关——简单可靠，但删库/替换数据库文件时要记得清池。

### F5 ⭐⭐ 动态拼 WHERE 会不会 SQL 注入？

**参考答案**：不会，因为**值**全部走 `AddWithValue` 参数（`@startTime` / `@endTime` / `@projectName`），只有**条件片段**（要不要加这一段 AND）由代码按布尔开关拼接，用户输入不参与 SQL 文本。`AddParameters` 里对 `null` 统一转 `DBNull.Value`，`MapToModel` 读字段用 `as string ?? ""`，`result` 缺失回退 `"未标定"`。

**加分**：`NormalizeTime()` 把 `/`、`.` 统一成 `-`，`TryParseExact("yyyy-MM-dd HH:mm:ss")` 解析失败时**视为不加该条件**而不是拼进 SQL；结束日期只给 10 位时补到 `23:59:59`，避免漏掉当天数据。

---

### F6 ⭐⭐ 合格率为什么在 SQL 里算，不拉回内存算？

**参考答案**：`SELECT COUNT(*), SUM(CASE WHEN result='不合格' THEN 1 ELSE 0 END) FROM DataModel{where}`，`rate = (total - ng) * 100.0 / total`。好处：只回传两个整数、与数据量无关；条件复用同一套参数化 WHERE，保证「表格里的记录」和「统计数字」口径一致；避免把全表读进内存再 LINQ 统计。
注意回答时补一句 `total == 0` 的除零保护和"未标定"是否计入合格率的分母口径（本项目未标定不算 NG，会计入分母，这是个可讨论的业务定义）。

---

### F7 ⭐⭐ `testTime` 是 TEXT，为什么字符串比较能做时间范围查询？

**参考答案**：因为格式被严格固定成 `yyyy-MM-dd HH:mm:ss`（定长、年月日时分秒按高位到低位排列、补零），字典序与时间序完全一致，`>= @startTime AND <= @endTime` 才成立。这是"约定优于类型"的做法，很脆弱：一旦有人写入 `2026-11-3 9:5:1` 或带时区/毫秒，排序立刻错乱。改进是存 `INTEGER` Unix 毫秒或 ISO 8601 + 严格校验，或用 SQLite 的日期函数配合统一格式。索引 `IX_DataModel_testTime` 让范围扫描走索引。

**加分**：`GetTimeRange()` 用 `MIN/MAX(testTime)` + `TryParseExact` 给查询页的日期控件定边界。

---

### F8 ⭐⭐ CSV 导出为什么要写 BOM？按钮写「导出excel」有问题吗？

**参考答案**：`UTF8Encoding(true)` 写 UTF-8 BOM，Excel 双击打开时会据此识别 UTF-8，否则中文按系统 ANSI（GBK）解释会乱码。`Csv()` 用双引号包裹字段、字段内双引号翻倍（`"` → `""`），处理产品名里的逗号/引号/换行；`SaveFileDialog` 过滤 `*.csv`。
文案「导出excel」名不副实——实际没有用 EPPlus/ClosedXML/NPOI，也不生成 `.xlsx`，只是 Excel 能打开的 CSV。这是要在简历和面试里主动纠正的点，别把 CSV 说成 Excel 导出。

## G. 可视化（ScottPlot 5）

### G1 ⭐⭐⭐ 曲线图中文变成方框 □，根因和修法？

**参考答案**（`plotView.ApplyChineseFont`）：ScottPlot 5 默认字体 `Segoe UI` 不含 CJK 字形，而 SkiaSharp 自己绘制文本，**不会走 WinForms/GDI+ 的字体回退机制**，缺字就画成豆腐块 □（不是编码问题，字符串本身是对的）。
修法两步：`string font = ScottPlot.Fonts.Detect("通道趋势测量值检测时间")` 用中文样本探测系统中可用的中文字体（本机实测 `Microsoft YaHei UI`）→ `plot.Font.Set(font)` 设置全局（注意会影响 `Fonts.Default`）→ **额外** `plot.Legend.FontName = font`，因为图例字体是独立属性，`Font.Set` 不覆盖它。

**验证**：用 SkiaSharp `plot.Render(canvas, 900, 450)` 离屏渲染出 PNG 检查中文，不必启动窗体——这个"不启 UI 验证渲染"的思路很加分。

---

### G2 ⭐ 时间轴怎么画的？

**参考答案**：把 `DateTime` 用 `ToOADate()` 转成 double 作为 X 值（OLE 自动化日期，1 天 = 1.0），`Add.Scatter(xs, ys)` 画线，再 `Axes.DateTimeTicksBottom()` 让底部刻度按日期时间格式化；标题/XLabel/YLabel/LegendText 用中文（配合 G1 的字体设置）。每次查询先 `Plot.Clear()` 再重建，`Refresh()` 重绘。

**追问**：`OADate 精度够吗？` → double 表示天数，毫秒级采样点够用；若要长期高频数据，可改成相对秒数或 `DateTime` 轴 + 自定义刻度。

### G3 ⭐ 为什么 `plotView` 的按钮事件要在 `.cs` 里手动绑？

**参考答案**：Designer 里 `plotView` 只绑了 `Load`，查询按钮的 `uiButton1.Click += uiButton1_Click` 是在代码里补的（阈值页的 8 个通道面板、4 个刀补按钮同理）。这提醒我们：**事件绑定事实来源是 `*.Designer.cs`**，有的页面 designer 生成、有的手动补，排查"按钮没反应"时两边都要看，且同一事件不要在两处重复绑定。

## H. 架构 / 设计 / 可维护性

### H1 ⭐⭐ 项目里为什么同时存在 `TICP.*` 和 `WinFormsApp3.*` 两个命名空间？

**参考答案**：项目文件从 `WinFormsApp3.csproj` 改名成 `TICP.csproj` 后，`RootNamespace` 随之变成 `TICP`，于是后加的 `Common/Helper/Model/Properties/Program` 都是 `TICP.*`；而 `Form1` 和 5 个 `View/*` 页面保留了 `WinFormsApp3.*`，因为它们的 `.Designer.cs` 与 `.resx` 嵌入资源名绑定在旧命名空间上，只改一半会报 `CS0234`（类型或命名空间不存在）。历史遗留的 `using WinFormsApp3.Helper/Model` 已清理干净。

**加分**：能讲出 `.resx` 的嵌入资源清单是按「命名空间.类名.resources」解析的，改名必须同步改资源逻辑名，否则运行时 `ResourceManager` 找不到资源——这正是没全量迁移的现实原因。

### H2 ⭐⭐ 讲一下分层，以及它的问题

**参考答案**：`Model`（`dataModel` 记录、`yuzhiModel` 标定数学）→ `Common`（全局状态 `mainCommon`、配置 `AppConfigStore`/`yuzhiCommon`、纯逻辑 `QualityCommon`）→ `Helper`（`ModbusRtuClient` 通信、`SqlHelper` 存储、`Log`、`FormShowHelper`）→ `View`/`Form1`（SunnyUI 界面）。
问题：`mainCommon` 把状态、通信客户端、数据库访问全塞进一个静态类，View 直接读全局数组，层与层之间是隐式耦合；没有接口、没有 DI、没有事件总线，采集逻辑还写在 `mainView` 里。改法见 A4。

### H3 ⭐⭐⭐ 你怎么给这个项目加单元测试？

**参考答案**：优先测纯逻辑、不测控件：
- `yuzhiModel.TryConvert`：正常两点、除零、参数缺失、NaN/Infinity、反向量程、超量程外推；

### H4 ⭐⭐ 数据量变大会怎么改？

**参考答案**：① 查询加 `LIMIT/OFFSET`（或键集分页）+ 总数统计，别 `GetAll()` 全量加载；② 采集与入库解耦：内存队列 + 批量事务（`BEGIN/COMMIT` 每 N 条），SQLite 单条自动提交很慢；③ 写库改异步 I/O，避免 UI 线程等；④ 分区/按月归档历史表，热数据留主表；⑤ 数值列改 REAL/INTEGER 并加复合索引；⑥ 趋势曲线做降采样（LTTB / 按时间桶聚合），不要把几万点全丢给 ScottPlot；⑦ 加 WAL 模式提升读写并发。

### H5 ⭐⭐ 报警机制现在做到哪一步？还缺什么？

**参考答案**：现状 = 采集循环里 `q.HasNg` 时 `Log.Warn($"通道 [{q.NgChannels}] 超差")` + 10s 限流，卡片灯变红；`simpleView` 第二个灯泡恒灰，注释写「保留给报警闪烁，暂不启用」。
缺：去重/状态机（从"超差"到"恢复"才记一条，而不是每帧刷）、声光提示与弹窗、操作员确认与备注、报警记录表与查询、分级（预警/严重）、与停机联锁。补齐时会把报警做成事件，由独立 `AlarmService` 订阅判定结果，而不是塞进采集循环。

---

### H6 ⭐ 全局异常和日志是怎么设计的？

**参考答案**：`Program.cs` 挂 `Application.ThreadException`（UI 线程未处理异常）+ `AppDomain.UnhandledException`（非 UI 线程），统一 `Log.Error` + MessageBox；对堆栈含 `WmDpiChangedBeforeParent` / `Font.ToHfont` 的高频 GDI+ 字体异常只记日志不弹窗，避免骚扰。`Log` 按 `Logs/yyyy-MM-dd/{Info,Warn,Error}/log_yyyy-MM-dd.txt` 分目录，`lock` 串行写，且整体 try/catch 吞掉日志自身的故障（日志不能把主程序搞崩）。
可改进：结构化日志（JSON + 级别 + 通道 + 耗时）、按大小滚动、异步写入、集中采集。

## I. 现场排错情景题（面试官最爱问"如果…你查哪里"）

### I1 点「隐藏通道」没反应

**参考答案**：先查 `mainView.Designer.cs` 有没有 `uiButton2.Click += uiButton2_Click;`（项目里就是漏绑过，注释有记录）；再看处理函数是否切了 `uiPanel2.Visible` 和 `channelsVisible`；最后确认没有在 Designer 与代码里重复绑定。

### I2 从「阈值设置」切回「数据测量」后，采集和当前值刷新都停了

**参考答案**：查生命周期挂载点。`FormShowHelper.formShow` 改 `Parent` 会重建句柄并触发 `HandleDestroyed`，若在那里 `readCTS.Cancel()` / `refreshTimer.Stop()`，切回来就不会恢复（页面还是缓存的那个对象，不会重新构造）。修法：改挂 `Disposed`，`Load` 加 `initialized` 幂等，CTS 只 Cancel 不 Dispose。

### I3 曲线标题/图例中文全是 □

**参考答案**：不是编码问题，是 ScottPlot 5 默认 `Segoe UI` 无中文字形 + SkiaSharp 不做字体回退。`Fonts.Detect(中文样本)` → `plot.Font.Set(font)` → 再单独设 `plot.Legend.FontName`（图例不被 `Font.Set` 覆盖）。离屏 `Render` 出 PNG 验证。

### I4 用旧版本留下的 `data.db` 一保存就报 `no such column: result`

**参考答案**：`CREATE TABLE IF NOT EXISTS` 不给已存在的表补列。用 `PRAGMA table_info` 探测 → `ALTER TABLE ADD COLUMN` → `UPDATE` 回填 → `CREATE INDEX IF NOT EXISTS`；若急着恢复，先备份 .db 再手工执行同样的 ALTER。注意默认连接池可能锁文件，替换前 `SqliteConnection.ClearAllPools()`。

### I5 拔掉 USB 转串口后日志文件暴涨、界面卡死

**参考答案**：三处一起看：① 采集线程是否每轮都抛异常并记日志 → 加 10s 限流；② 是否每轮都尝试重连 → 用 `Environment.TickCount64` 做 3s 间隔；③ 后台线程是否弹了 MessageBox（同步阻塞且不属于 UI 线程）→ 一律改为更新状态灯 + 日志，只有用户手动操作才允许弹窗；④ 失败后要 `Disconnect()` 把 `IsConnected` 置 false，否则下一轮仍以为在线。

### I6 关闭程序再打开，提示 COM 口被占用

**参考答案**：`SerialPort` 未释放或后台任务没退出，进程残留（也可能是别的程序占用）。检查退出路径：`Disposed` 里 `Cancel()` → 捕获 `OperationCanceledException` 退出循环 → `finally` 中 `Disconnect()`/`Dispose()` 串口；`Application.Run` 结束后确认没有前台线程存活（Task 默认线程池是后台线程，不会阻止进程退出，裸 `Thread` 前台线程会）。另外 `Disconnect()` 里无条件先清理旧连接再 `Open()`，避免同进程内重复占用。

### I7 保存数据成功但表格没出现新行 / 出现两行

**参考答案**：先看是不是 `SqlHelper.Insert` 抛异常被 catch 后仍执行了 `bindingList.Add`（项目是「先写库成功后才 Add」，正确）；再看同一事件是否在 Designer 和 `.cs` 里绑了两次导致插入两次（会看到 Id 连续跳号）；再看 `DataGridView` 的 `DataPropertyName` 是否与 `dataModel` 属性名一致、`AutoGenerateColumns` 设置是否把动态追加的判定列冲掉。
